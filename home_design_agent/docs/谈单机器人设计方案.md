# 谈单机器人（TalkBot）技术设计方案

> 版本：v1.0（设计稿）
> 日期：2026-08-24
> 状态：待评审 / 待落地
> 适用范围：`home_design_agent` 项目（Arch AI 家装设计 Agent）

---

## 一、背景与目标

现有 Arch AI 平台已跑通「毛坯照 → AI 效果图 → 方案报告 → 套餐付费 → 下单履约」的完整链路，但需求采集环节仍是**表单式单次留资**（`design/models.py::CustomerRequirement`），缺少一个能主动对话、理解处境、共情顾客、并把高意向用户推进到下单的**谈单机器人**。

### 1.1 核心目标

- **共情顾客**：先接住情绪、理解处境，建立信任，而不是机械问答。
- **打动顾客**：在信任建立后，用精准的价值输出与恰到好处的推进促成下单。
- **推进到下单**：最终把高意向对话转化为 `HomeOrder`（我的家项目订单），复用现有 `design` / `payments` 体系。

### 1.2 非目标（本期不做）

- 不做语音通话 / 实时音视频。
- 不做施工监管、工地巡检等交付后环节。
- 不做独立产品，完全寄生在 Arch AI 平台内。

---

## 二、现状盘点：可复用 vs 需新建

| 能力 | 现有实现（文件位置） | 谈单机器人的用法 |
| --- | --- | --- |
| 画像载体 | `design/models.py::Owner` / `Project` | 作为画像底座，谈单补齐字段后写回 |
| 线索转化 | `design/models.py::Lead` + `Project.Status` | 谈单最终产出 Lead / 推进项目状态 |
| 需求收集 | `design/models.py::CustomerRequirement` | 保留为"表单兜底"，升级为对话驱动 |
| 方案生成 | `design/services.py::build_preview_schemes` | 对话收口时自动生成预方案 |
| 效果图 | `design/models.py::RenderJob` + 工作流 | 对话中按需触发效果图 |
| 报告/下单 | `HomeReport` / `HomeOrder` / `OrderDetail` | 谈单终点：生成报告并下单 |
| **流程编排引擎** | `design/models.py::RenderWorkflow` + `WorkflowStep` | **核心复用点**：照搬为对话编排引擎 |
| **Prompt 控制模块** | `design/models.py::PromptModule` | 复用为"话术模块化"，话术文本只存后端 |
| 知识素材 | `Furniture` / `ServiceProvider`（含 `cases`）/ `Designer` | 直接作为 RAG 案例库/方案库素材 |
| 文本 LLM 调用 | `design/imagegen.py::_call_chat_design_note` | 复用 OpenAI 兼容 chat 调用模式 |
| 用户/支付 | `users` / `payments` | 谈单挂到登录用户 + 额度体系 |

**核心缺口**：没有多轮对话循环、没有共情/心理洞察层、没有主动提问引擎、没有话术/异议 RAG 库。

## 三、总体架构

新增一个 `talkbot` 应用，与 `design` 平行，复用 `design` 的 `Owner` / `Project` / `Lead` / `RenderWorkflow` 模式。

```text
                    用户浏览器（Vue SPA / 管理后台）
                              │ HTTPS
                              ▼
                        Nginx :80 → gunicorn :8000
                              │
              ┌───────────────┼──────────────────┐
              ▼               ▼                  ▼
          design/          talkbot/          users/ payments/
       (项目/方案/订单)   (对话/画像/编排/RAG)  (认证/额度)
              └───────────────┼──────────────────┘
                              ▼
                   PostgreSQL（生产）/ SQLite（本地）
                              │
              ┌───────────────┴──────────────────┐
              │ 外部依赖：文本 LLM（DeepSeek 兼容）│
              └──────────────────────────────────┘
```

### 3.1 后端目录规划（新增）

```text
talkbot/
├── apps.py          # AppConfig
├── models.py        # Conversation / Message / CustomerProfile / TalkWorkflow / TalkStep / KnowledgeBase / KnowledgeDocument
├── empathy.py       # 共情模块：处境/家庭/经济/近况 抽取
├── psychology.py    # 心理模块：情绪/性格/弱点/信任/意向 判断
├── strategy.py      # 决策模块：本轮动作 + 下一问字段
├── rag.py           # RAG 检索：话术/案例/报价/工艺/FAQ
├── llm.py           # LLM 封装：复用 OpenAI 兼容 chat
├── engine.py        # 对话编排循环（串联以上模块）
├── serializers.py   # DRF 序列化
├── views.py         # 会话/消息 API
├── urls.py          # /api/talkbot/*
├── admin.py         # 后台注册（会话回放/画像/知识库/编排）
└── migrations/
```

## 四、数据模型设计

### 4.1 会话与消息

| 模型 | 关键字段 | 说明 |
| --- | --- | --- |
| `Conversation` | `user`、`project`(FK，可空)、`stage`、`last_action`、`summary`、`created_at` | 一次谈单会话，`stage` 为销售阶段状态机 |
| `Message` | `conversation`、`role`(user/assistant/system)、`content`、`intent`、`emotion`、`question_asked`、`created_at` | 多轮历史，结构化字段供复盘与画像更新 |

### 4.2 客户画像 `CustomerProfile`

画像字段对齐三大模块（共情/心理/销售），是循环询问的采集目标与决策依据。

| 模块 | 字段 | 类型 | 来源 |
| --- | --- | --- | --- |
| 共情·处境 | `situation` | 文本 | 对话抽取 |
| 共情·家庭 | `household`、`has_kids`、`kids_age`、`has_elderly`、`pets` | 结构化 | 循环询问 |
| 共情·经济 | `income_tier`、`budget_min/max`、`decision_power` | 结构化 | 循环询问 |
| 共情·近况 | `recent_events`（婚期/换房/升学/入住时间） | 文本+标签 | 对话抽取 |
| 心理·情绪 | `emotion`、`emotion_trace` | 枚举+数组 | 每轮识别 |
| 心理·性格 | `persona_type`（理性/感性/冲动/谨慎） | 枚举 | 多轮判断 |
| 心理·弱点 | `pain_points`（甲醛/增项/工期/预算/审美） | 数组 | 抽取+映射 |
| 心理·信任/意向 | `trust_score`、`intent_score` | 0–100 | 每轮更新 |
| 销售·阶段 | `stage` | 枚举 | 状态机 |
| 销售·缺口 | `missing_fields` | 数组 | 驱动下一问 |

### 4.3 对话编排引擎（复用工作流模式）

仿 `RenderWorkflow` + `WorkflowStep`，新增 `TalkWorkflow` + `TalkStep`。

`TalkStep.Kind` 候选步骤类型：

```text
intake          # 接收输入
emotion         # 情绪识别
intent          # 意图识别
profile_update  # 画像增量更新
stage_judge     # 销售阶段判断
strategy_plan   # 策略决策（共情/提问/价值/促单 + 下一问字段）
rag_retrieve    # RAG 检索
llm_generate    # LLM 生成回复
guard           # 安全/合规过滤
output          # 输出
log             # 记录轨迹
```

与 `RenderWorkflow` 一致的设计原则：

- **后台可编排**：运营在 `/admin/talkbot/talkworkflow/` 增删步骤、调顺序、改参数，不改代码。
- **失败容错**：单步失败写 `workflow_log` 不阻塞整轮，降级到规则文案。
- **执行轨迹**：每轮保留状态/耗时/摘要，后台可回放排查。

### 4.4 RAG 知识库

| 模型 | 关键字段 | 说明 |
| --- | --- | --- |
| `KnowledgeBase` | `name`、`category`（话术/案例/报价/工艺/FAQ/异议） | 知识库分桶 |
| `KnowledgeDocument` | `base`(FK)、`content`、`embedding`、`tags`、`meta` | 文档与向量，`tags` 用于路由过滤 |

`embedding` 可选：MVP 可用**关键词/标签召回 + Rerank**，规模上来后再接向量库（避免引入额外依赖）。

## 五、模块设计

### 5.1 共情模块 `empathy.py`

职责：判断"这个人正处在什么境地"，给出有依据的共情回应。

| 维度 | 判断内容 | 典型信号 | 话术目标 |
| --- | --- | --- | --- |
| 客户处境 | 面临的问题/场景 | 主动倾诉、关键词（"最近很累""刚换工作""孩子要上学"） | 复述处境，确认理解 |
| 家庭信息 | 婚姻、子女、老人、家庭结构 | 对话自然提及 | 判断责任压力、决策动因 |
| 经济情况 | 收入、预算、消费能力 | 价格敏感、预算试探 | 匹配价位、避免越级 |
| 客户近况 | 近期重大事件 | 买房/换工作/生病/升学/开店 | 识别需求触发点（Timing） |

**关键**：共情不是"我也理解你"，而是「复述 + 提炼 + 情感命名」。输出为 `CustomerProfile` 字段增量 + 一段共情话术（注入 LLM）。

### 5.2 心理判断模块 `psychology.py`

| 维度 | 判断内容 | 用途 |
| --- | --- | --- |
| 情绪识别 | 焦虑/犹豫/期待/不信任/防御 | 决定本轮先共情还是先给价值 |
| 性格类型 | 理性/感性/冲动/谨慎 | 切换说服策略（数据 vs 故事 vs 紧迫感） |
| 真实需求 | 表面需求 vs 深层动机 | 表面"预算不够"深层"怕选错" |
| 弱点判断 | 核心焦虑/恐惧/渴望 | 找到打动点，守住道德底线 |
| 信任度 | `trust_score` | 判断能否进入促单 |
| 购买意向 | `intent_score` | 决定推进力度 |

家装客户心理弱点映射：

| 弱点 | 具体焦虑 | 打动力策略 |
| --- | --- | --- |
| 健康焦虑 | 甲醛伤害孩子/孕妇 | 环保等级 + 入住前检测 + 案例 |
| 怕被坑 | 增项/偷工减料/货不对板 | 透明报价 + 增项规则 + 可验收 |
| 预算失控 | 隐性成本/超支 | 一开始给"总价天花板"，提前说坑 |
| 工期拖延 | 影响入住/婚期/租金 | 工期节点 + 违约条款 |
| 面子比较 | 怕装丑、比邻居差 | 风格案例 + 设计师背书 |
| 审美不自信 | 选择太多、怕配错 | 给"推荐方案"而非无限选项 |
| 决策疲惫 | 货比三家后更纠结 | 权威背书 + 差异化 + 轻促单 |

> ⚠️ 合规红线：弱点判断只用于"更精准地帮助客户"，绝不制造恐慌、夸大后果、情感绑架。

### 5.3 销售/策略模块 `strategy.py`

销售阶段状态机：

```text
破冰 → 需求挖掘 → 方案匹配 → 异议处理 → 促单 → 下单 → 后续维护
```

| 阶段 | 目标 | 本轮策略倾向 | 是否提问 |
| --- | --- | --- | --- |
| 破冰 | 建立信任 | 共情 + 轻松开场 | 少量开放问 |
| 需求挖掘 | 补全画像 | 循环询问（精准提问） | 高 |
| 方案匹配 | 呈现价值 | RAG 案例 + 价值输出 | 中 |
| 异议处理 | 消除顾虑 | 共情 + 证据 + 反问 | 中 |
| 促单 | 推动成交 | 紧迫感/从众/权威背书 | 低 |
| 下单 | 确认 + 收尾 | 明确权益 + 下一步 | 低 |

决策引擎每轮输出**单一主导动作**：

```json
{
  "action": "ask|empathize|value|close",
  "question_field": "budget",
  "rag_query": "环保案例 儿童房",
  "strategy": "环保价值输出",
  "reason": "画像缺预算，情绪焦虑，阶段=需求挖掘"
}
```

### 5.4 RAG 知识库 `rag.py`

| 库 | 数据来源 | 触发场景 |
| --- | --- | --- |
| 共情话术库 | 新建 `KnowledgeDocument` | `emotion` 命中 |
| 异议处理库 | 新建（含证据） | 客户提异议 |
| 案例库 | **复用** `ServiceProvider.cases` + 生图案例 | 建信任/风格确认 |
| 报价库 | **复用** 套餐 `PricingPlan` + 方案 `budget_tier` | 客户问价 |
| 工艺/环保库 | 新建 | 怕甲醛/工期/质量 |
| FAQ | 新建 | 事实追问 |

检索策略：先按 `{痛点, 阶段, 画像}` 路由（与 `RenderWorkflow.match_for_job` 的标签匹配思路一致），再召回 + Rerank。

### 5.5 LLM 封装 `llm.py`

使用 DeepSeek 官方 OpenAI-compatible 调用模式。配置优先从后台“生成配置(API)”的
加密字段读取，未填写后台 Key 时回退服务器环境变量：

```python
from openai import OpenAI
config = load_deepseek_config()
client = OpenAI(api_key=config.api_key, base_url=config.api_base)
resp = client.chat.completions.create(
    model=config.model,
    messages=[...],
    temperature=0.55,
    stream=False,
)
```

多角色 prompt 由决策层路由（共情者 / 顾问 / 销售 / 收尾员），人设 + 策略 + RAG 检索内容 + 画像统一注入。发送前移除手机号、邮箱、证件号、银行卡号和详细地址；DeepSeek 不可用时继续输出规则回复。

## 六、对话循环流程（回合级）

```text
client ──输入──▶ intake(接收输入)
                  │
       ┌──────────▼──────────┐
       │ emotion(情绪识别)    │──▶ CustomerProfile.emotion
       │ intent(意图识别)     │
       └──────────┬──────────┘
                  ▼
       profile_update(画像增量更新) ──▶ 更新 missing_fields / trust / intent
                  ▼
       stage_judge(销售阶段判断) ──▶ Conversation.stage
                  ▼
       strategy_plan(决策引擎) ──▶ {action, question_field, rag_query}
                  ▼
       rag_retrieve(知识库检索) ──▶ 话术/案例/报价/工艺/FAQ
                  ▼
       llm_generate(带人设+策略+检索+画像)
                  ▼
       guard(合规过滤) ──▶ output ──▶ client
                  ▼
       log(记录轨迹) ──▶ 回到下一轮
```

### 循环询问三原则

1. **一次一问**（最多两问），绝不问卷式连珠炮。
2. **先接后问**：先回应客户刚说的话，再自然引出问题。
3. **有目的**：每个问题对应一个待补全的画像字段，不闲聊。

### 退出条件

- 达成下单 → 转入下单收尾。
- 连续 N 轮信任度下降 / 客户明确拒绝 → 礼貌收尾，避免死缠。

## 七、集成到下单（HomeOrder）链路

谈单机器人的"成功"是**推进到下单**，而不是线上硬成交。收口动作复用现有 `CustomerRequirementViewSet.perform_create` 与 `HomeOrderViewSet.perform_create` 的写法。

### 7.1 收口时自动建单（伪代码）

```text
识别到促单成功 / 客户确认下单
  │
  1. 写回 CustomerProfile → Owner / Project
     - Owner.get_or_create(phone)
     - Project.create(title, city, community, budget, requirement_summary, status=REQUIREMENT)
  2. 生成预方案
     - build_preview_schemes(project)   # design/services.py
  3. 生成报告快照
     - HomeReport.create(user, project, report=方案摘要)
  4. 创建订单
     - HomeOrder.create(user, project, report, items, amount_min/max, total_amount)
     - OrderDetail.sync_from_order(order)
     - report.status=ORDERED, project.status=SIGNED
```

这样订单会正常出现在用户「我的家」/ 订单列表，走现有支付与后台确认流程，不重复造轮子。

### 7.2 边界处理

- 未登录用户：对话到留资节点时引导注册/登录后再下单。
- 信息不全：`CustomerProfile.missing_fields` 非空时，不强制下单，继续循环询问补齐。
- 表单兜底：对话任意时刻可转 `CustomerRequirement` 表单，保证链路不断。

## 十一、风险与合规

- **话术安全**：`guard` 步骤过滤夸大承诺、误导表述、联系方式诱导；不输出绝对化承诺（"一定无甲醛"）。
- **隐私**：家庭/经济/近况属敏感信息，仅用于画像与履约，落库需脱敏，权限隔离。
- **成本**：文本 LLM 按 token 计费，MVP 用规则兜底 + 缓存，控制调用量；后续接计量。
- **幻觉**：报价、工期、环保参数必须来自 RAG/结构化库，不允许 LLM 自由发挥。

---

## 十二、验收标准
