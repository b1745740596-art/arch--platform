# 网站架构分析：home_design_agent

> 面向当前仓库的现状梳理、模块清单与差距分析。基于 `README.md`、`config/settings.py`、`docker-compose.yml`、`deploy/` 与三个业务应用综合整理。

## 一、现状总览

当前架构是一个 **Django 单体 + Vue 单端口托管** 的 Web 应用，功能域已经拆成 `users` / `design` / `payments` 三个应用，并用 Docker Compose 承载生产形态。

- 前端：Vue 3 + Vite + vue-router + pinia + axios + i18n，构建产物由 Django 托管，无跨域
- 后端：Django 5 + DRF，本地 SQLite、生产 PostgreSQL
- 部署：Nginx（静态/媒体直发 + 长超时代理）+ gunicorn + PostgreSQL
- 领域：家装设计 Agent（户型识别、需求对话、方案生成、BOM、撮合、施工监管）
- 商业化：按次计费额度 + Stripe / 微信支付 / 支付宝

## 二、架构图

```text
                    用户浏览器（Vue SPA / 管理后台）
                              │ HTTPS
                              ▼
                        Nginx :80
              ┌───────────────┼────────────────┐
              │ /static       │ /media         │ /（应用与 API）
              ▼               ▼                ▼
         staticfiles      media 卷        gunicorn :8000
                                              │
                 ┌──────────────────┬─────────┴─────────┬──────────────┐
                 ▼                  ▼                   ▼              ▼
              config            users              design          payments
           (配置/路由/         (认证/资料)        (核心业务/工作流)   (套餐/额度/订单)
           日志/安全)
                 └──────────────────┴─────────┬─────────┴──────────────┘
                                              ▼
                            PostgreSQL（生产） / SQLite（本地）
                                              │
                   ┌──────────────────────────┴──────────────────────────┐
                   │ 外部依赖：AI 生图服务、Stripe、微信支付、支付宝、短信网关 │
                   └─────────────────────────────────────────────────────┘
```

请求链路：Nginx → gunicorn → Django 视图/DRF → 数据库或外部服务 → JSON/静态文件返回。

## 三、模块清单

### 1. 前端模块

| 模块 | 位置 | 职责 |
| --- | --- | --- |
| 路由 | `frontend/src/router/index.js` | 页面路由与 SPA 回落 |
| 状态管理 | `frontend/src/stores/*` | 鉴权、账户、账单、健康检查、工作台队列 |
| 页面 | `frontend/src/views/*` | 首页、登录注册、工作台、项目、账单、后台管理 |
| API 客户端 | `frontend/src/api/client.js` | axios 封装、CSRF、统一错误处理 |
| 输入校验 | `frontend/src/utils/validation.js` | 与后端同口径的图片/需求/模块约束 |
| 国际化 | `frontend/src/i18n/*` | 中英文文案 |
| 多窗口工作台 | `frontend/src/views/StudioView.vue` | 并行生成、排队、发散选项 |

### 2. 后端业务模块

| 模块 | 位置 | 职责 |

| 用户系统 | `users/` | 注册登录、手机/邮箱验证码、资料、权限、后台用户管理 |

| 支付与额度 | `payments/` | 套餐、订单、额度流水、渠道回调、营收统计 |

### 3. 数据与基础设施模块

| 模块 | 位置 | 说明 |
| --- | --- | --- |

## 四、差距分析

### 已具备且做得不错

- 配置全部环境变量化，开发/生产切换清晰
- 单端口托管与 SPA 回落，避免本地跨域问题
- 长请求超时链路完整：`nginx 600s > gunicorn 600s > 前端 360s > 后端 300s`
- 支付多渠道 + webhook + 额度流水，并有 mock 模式便于联调
- 幂等种子、WAL/写重试、后台可编排工作流，具备一定工程化基础
- CI 已含 `check --deploy`、测试与前端构建

### 待补齐模块（按优先级）

**P0：上线安全与可靠性**

- [ ] 密钥管理：支付/AI Key 目前依赖服务器 `.env` 与后台字段，建议引入 Secret 管理或加密存储
- [ ] HTTPS 与 WAF：当前仓库依赖外层 SLB/nginx 卸载 TLS，需确认正式环境已配置
- [ ] 数据库自动备份：`DEPLOY.md` 给了手工命令，但缺少定时任务与恢复演练
- [ ] 媒体备份与清理：效果图持续增长，缺生命周期清理和跨机迁移机制
- [ ] 日志采集与告警：目前只输出 stdout，缺持久化日志、错误告警、慢请求监控

**P1：容量与可扩展性**

- [ ] 异步任务队列：生图是同步长请求，是最大瓶颈；建议引入 Redis + Celery/RQ + 前端轮询/Webhook
- [ ] 对象存储 + CDN：效果图应迁到 OSS/S3 + CDN，避免本地卷单点、加速加载
- [ ] 缓存层：Redis 用于会话、热点数据、验证码限流、生成结果缓存
- [ ] 限流与防刷：登录、验证码、生成、支付回调需要 Rate Limit
- [ ] 可观测性：接入 Sentry、APM、指标采集和告警

**P2：工程与治理**

- [ ] 定时任务：渲染清理、对账、报表、备份
- [ ] 审计日志：管理员操作与关键状态变更留痕
- [ ] 测试覆盖：补充生图链路、支付回调、额度扣减的关键路径测试
- [ ] Feature Flag / 灰度：工作流、Prompt 模块、套餐上下线的可控发布
- [ ] 安全扫描：依赖漏洞扫描、静态代码检查、敏感信息扫描
- [ ] 成本治理：AI 调用计量、图片存储与带宽成本统计

## 五、建议演进路线

1. **短期（MVP 上线前）**：完成 P0，补上备份、监控告警、日志采集、HTTPS 校验。
2. **中期（规模化）**：把生图改为异步任务，引入 Redis + 对象存储 + CDN，加限流。
3. **长期（平台化）**：按 PRD 继续拆分 `design` 下的业务模块，评估是否从单体走向模块化单体或微服务，并强化多租户、审计、成本与运营治理。
